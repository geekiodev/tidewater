# Build log

Running log of what the build agent did for each prompt in the prompt pack, including what was skipped or simplified and why.

## Environment facts that affect the whole build

- **No Docker images.** The Docker daemon starts, but pulls from Docker Hub / ECR are refused by the network proxy, so `npx supabase start` (which needs Docker images) **cannot run here**. Nothing in this build has been run against the real Supabase stack (GoTrue auth, PostgREST, Supabase's own Postgres image).
- **Real Postgres is available.** The local PostgreSQL 16 cluster was started and is used to apply the migrations and run the database tests. Supabase's `auth` schema, roles and `auth.uid()` don't exist in plain Postgres, so tests load a small shim (`tests/db/supabase-shim.sql`) that recreates just those pieces. Supabase local uses Postgres 17; tests here ran on 16.
- **No credentials.** No Stripe, Supabase or Anthropic keys exist here. Only dummy values appear, in `.env.example`. Nothing has been called against Stripe or Anthropic.
- **No docs access.** The Anthropic docs couldn't be fetched, so the model ID is an environment variable (`ANTHROPIC_MODEL`, default `claude-haiku-4-5`). Confirm it against current docs before launch.

## Prompt 0: Context

**Built**
- Next.js 16.4.2 app (App Router, TypeScript, `src/` layout) scaffolded with `create-next-app`; Supabase CLI project initialised (`supabase/config.toml`).
- Dependencies: `@supabase/supabase-js`, `@supabase/ssr`, `stripe`, `@anthropic-ai/sdk`, `zod`, `server-only`; dev: `vitest`, `pg`, `supabase` CLI.
- `src/lib/env.ts`: every setting read from environment variables, validated with zod, grouped and validated lazily so the app builds without secrets. Stripe keys must be `sk_test_` (test mode only).
- `.env.example` with dummy values only; `.gitignore` ignores all `.env*` except `.env.example`.
- Landing page; template assets and the Google Fonts import removed (the build fetches fonts from Google, which isn't reachable here, and it adds a third-party origin to the CSP).
- Supabase auth config hardened: 12-char passwords with mixed case and digits, email confirmation on, secure password change on, redirect URLs limited to the local callback.
- npm scripts: `typecheck` (runs `next typegen` first because `next-env.d.ts` is generated and git-ignored), `lint` (zero warnings allowed), `test`.

**Decisions / simplifications**
- `cacheComponents` was on in the Next 16 template; turned **off**. Every page is per-user, and the nonce-based CSP (Prompt 3) needs dynamic rendering anyway. Less to get wrong in a first version.
- `@types/node` set to `^22` to match the Node 22 runtime (the template's `^20` conflicted with vitest 5's peer range).
- `AGENTS.md` generated by Next.js is kept (it only tells agents to read the bundled Next docs; no secrets).

**Known issues**
- `npm audit` reports 5 high-severity advisories, all in the `braces`/`micromatch` chain under `eslint-config-next` (dev-only lint tooling, not shipped). The only "fix" npm offers is downgrading `eslint-config-next` to 14.x, which would break linting on Next 16. Left as is; revisit when upstream updates.

## Prompt 1: Workspaces, accounts and access

**Built**
- Migration `supabase/migrations/20261019000100_workspaces_and_access.sql`: `workspaces`, `workspace_members` (role `owner`/`member`), `workspace_invitations`, and an internal `private.rate_limits` table.
  - RLS enabled on every table. Membership checks go through `SECURITY DEFINER` helpers in a non-exposed `private` schema.
  - Supabase's default "grant everything to anon/authenticated" is revoked; each table gets back only the privileges it needs. Owners can update only the workspace `name` column (column-level grant), so billing columns added later can't be edited from the browser.
  - Workspace creation at sign-up is a trigger on `auth.users` that reads `workspace_name` from sign-up metadata and makes the user the owner.
  - `accept_invitation(token)`: checks the token hash, expiry, and that the signed-in user's **confirmed** email matches the invitation. Role is always `member`.
  - `rate_limit_hit(bucket, limit, window)`: fixed-window counter in Postgres, callable only by `service_role`.
- Auth (`src/app/auth/actions.ts`, `/login`, `/signup`, `/auth/callback`): Supabase email/password with email confirmation (PKCE code exchange). Login errors are generic so the form doesn't reveal which emails have accounts.
- Server-side access control in two layers:
  - `src/proxy.ts` (Next 16's renamed middleware) verifies the session with `supabase.auth.getUser()` on every request. Signed-out page requests are redirected to `/login`; signed-out API requests get 401. Public: `/`, `/login`, `/signup`, `/auth/callback` (`src/lib/access.ts`).
  - Every page, server action and route handler calls `requireUser` / `requireWorkspace` / `requireOwner` (`src/lib/auth.ts`) itself. Workspace and role are always read from the database for the verified user.
- Rate limiting (`src/lib/rate-limit.ts`): login 20 per 15 min per IP and 8 per 15 min per email; sign-up 5 per hour per IP. Identifiers are SHA-256 hashed before storage. The limiter **fails closed**: if it can't reach the database, the attempt is refused.
- Team page (`/settings/team`): list members; the owner can invite by email, revoke pending invitations and remove members. Onboarding page for a signed-in user with no workspace. Invitation accept page (`/invite/[token]`), which accepts only on POST.
- `next` redirect parameters are restricted to same-site relative paths (open-redirect guard).
- Smoke-tested with `next start` and no Supabase running: `/`, `/login`, `/signup` return 200; `/settings/team`, `/onboarding` and `/invite/...` redirect to login; `/api/*` returns 401.

**Simplified / not done**
- **Invitation emails aren't sent.** No email provider is configured, and Supabase's built-in mailer only sends auth emails. Instead, the owner is shown a one-time invite link to send themselves. The invitation is still bound to the invitee's email: only a signed-in user with that confirmed email can accept. Wiring a transactional email provider is a follow-up.
- **One workspace per user** (unique constraint on `workspace_members.user_id`). This avoids a "current workspace" switcher, which would have to trust a workspace ID from the browser. Someone already in a workspace can't accept an invitation to another one.
- No way to change a member's role, transfer ownership, delete a workspace, or for a member to leave. Owners can't remove themselves.
- The IP used for rate limiting comes from `X-Forwarded-For`. That header can be spoofed unless the app sits behind a proxy that sets it, which is why there's also a per-email limit. Supabase Auth's own rate limits (`[auth.rate_limit]` in `config.toml`) also apply.
- `src/lib/database.types.ts` is hand-written, because `supabase gen types` needs the Docker stack. Regenerate it once the stack runs.
- Invitation tokens travel in the URL path (`/invite/<token>`), so they can appear in server access logs. They're single-use, expire after 7 days, and are stored only as hashes.
- Migration checked by applying it to the local Postgres 16 with the test shim, plus a manual RLS smoke test (user A sees only workspace A and can rename only it; `anon` gets permission denied). Automated tests come in Prompt 5.

## Prompt 2: Contacts and notes

**Built**
- Migration `20261019000200_clients_contacts_notes.sql`: `clients`, `contacts` (name, email, phone, job title), `notes`.
  - RLS on all three, limited to workspace members.
  - Contacts and notes reference their client through a **composite foreign key `(client_id, workspace_id)`**, so a row can't be attached to another workspace's client even if the app passes a foreign client id. RLS alone only checks the row's own `workspace_id`, so this closes a cross-tenant gap.
  - Column-level UPDATE grants, so `workspace_id`, `client_id`, `created_by` and `author_id` can't be changed after insert.
  - Length limits as CHECK constraints, mirroring the app's schemas.
  - Notes: any member can read and add; only the author can edit; the author or the workspace owner can delete.
- Server actions (`src/app/(app)/clients/actions.ts`) for create, update and delete of clients, contacts and notes. Each one re-checks the session, gets the workspace on the server, validates with zod (`src/lib/validation/crm.ts`) and writes through the user's RLS-bound client, with an explicit `workspace_id` filter as well.
- Limits: client name 200, website 300 (must be http/https, so `javascript:` links can't be stored), contact name 200, email 254, phone 50, job title 200, note 10,000 characters, search 100. Lists are paginated: default 25, **maximum 50** per page, maximum page 1000. Out-of-range values fall back to the default rather than erroring.
- Pages: `/clients` (search, paginated list, add form) and `/clients/[id]` (contacts and notes, each paginated; inline edit; delete with confirmation; client details). The default landing page after login is now `/clients`. Empty states say what to do next; there's no sample data. Note text is rendered as plain text.
- Error reporting (`src/lib/errors/report.ts`, `src/instrumentation.ts`): one reporter for caught errors and for uncaught server errors (`onRequestError`). It writes scrubbed JSON to stderr:
  - values under personal-data keys are redacted;
  - email addresses, phone-like numbers, quoted values and Postgres `Key (...)=(...)` details are stripped from messages and stacks;
  - query strings are dropped from request paths, and objects aren't serialised.
  - `setErrorSink()` is the hook for a hosted service later.
  - Users only see generic messages (`src/lib/db-errors.ts`, `src/app/error.tsx`).

**Simplified / not done**
- The error sink is stderr only; no hosted error tracker is wired up (no credentials). The scrubbing is pattern-based, so it **can miss personal data** in unexpected formats (e.g. a name inside an unquoted error message). It also over-redacts some things, such as dates and IP addresses, which look like phone numbers. Next.js's own dev-server error overlay and its default console logging of uncaught errors are outside this reporter.
- No JSON REST API for clients/contacts/notes. Everything goes through server-rendered pages and server actions; the page-size caps apply to those list queries.
- No contact search, sorting options, or move-contact-to-another-client. Deleting a client deletes its contacts and notes (cascade), with a confirmation prompt.
- Migration applied to local Postgres with the shim; full RLS isolation tests come in Prompt 5. The UI has not been clicked through against a live Supabase (not available here).

## Prompt 3: Billing

**Built**
- Migration `20261019000300_billing.sql`:
  - Subscription columns on `workspaces`: Stripe customer and subscription ids, `plan`, `subscription_status`, `current_period_end`, and `billing_event_at`, which guards event ordering. The browser role can read these but can't write them (only `name` is UPDATE-granted).
  - `private.stripe_events` records processed event ids.
  - `apply_stripe_event(...)`, callable only by `service_role`, records the event id and applies the change in **one transaction**. A redelivered event returns `duplicate` and changes nothing. It also:
    - ignores older events that arrive after newer ones (`stale`);
    - won't let an update about an old subscription cancel the current one;
    - rejects a customer id that doesn't match the workspace's (`customer_mismatch`).
  - The RLS **insert** policies on clients, contacts and notes now also require `private.workspace_is_active()`, i.e. status `active` or `trialing` with a known plan. Inactive workspaces can still read, edit and delete, but can't create, and that's enforced in the database.
- Plans (`src/lib/billing/plans.ts`): `starter` and `team`. The browser sends only the plan key, validated against an enum; the Stripe price id comes from server env vars. Promotion codes are disabled, and no amount or discount is read from the request.
- Checkout and Billing Portal (`/settings/billing`, owner only). The Stripe customer id is read from the database. `workspace_id` goes into session metadata, `client_reference_id` and subscription metadata, all set server-side.
- Webhook `POST /api/stripe/webhook`:
  - The logic lives in `src/lib/billing/webhook.ts`, kept free of framework code so it can be tested.
  - The signature is verified with `stripe.webhooks.constructEvent` on the raw body for **every** event, before anything is parsed (default 5-minute timestamp tolerance). Payloads over 512 KB are rejected.
  - Handles `checkout.session.completed` (links the customer) and `customer.subscription.created/updated/deleted`.
  - If the store fails, it returns 500 so Stripe retries; the transaction rolled back, so the retry is safe.
- App-level gating: create actions return a friendly message when the subscription isn't active, and a banner in the app layout explains the read-only state.
- Security headers:
  - The proxy sets a **nonce-based CSP** on every response: no `unsafe-inline` scripts in production, `frame-ancestors 'none'`, `connect-src 'self'`, and `form-action` limited to self plus Stripe Checkout/Portal.
  - Also sent: **HSTS** (2 years, includeSubDomains, preload; not in dev), `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, and COOP/CORP. Static assets get the non-CSP headers from `next.config.ts`.
  - The root layout reads `headers()` so every page renders dynamically and gets a fresh nonce.
- CSRF (`src/lib/security/csrf.ts`, enforced in the proxy for every non-GET request): the `Origin` must match the app's origin, falling back to `Sec-Fetch-Site: same-origin`, and requests with neither are rejected. This is on top of SameSite=Lax session cookies and Next's own Origin/Host check on Server Actions. Only the Stripe webhook is exempt, because its signature authenticates it.
- Smoke-tested on a production build:
  - CSP, HSTS and the other headers are present, and script tags carry a per-request nonce.
  - A cross-site POST returns 403, and so does a POST without an Origin header.
  - The webhook returns 400 for a missing or invalid signature.

**Simplified / not done**
- **Nothing has been run against Stripe.** No test-mode keys are available, so creating checkout and portal sessions is untested. Signature verification and duplicate handling are tested locally in Prompt 5 with Stripe's own test-signature helper.
- Prices are shown only at checkout; the billing page doesn't fetch amounts from Stripe.
- No free trial. A brand-new workspace can't create records until it subscribes. This follows "without an active subscription" literally; reconsider for onboarding.
- `past_due` counts as **inactive** (strict reading). Many SaaS products keep access during Stripe's retry window; this is a product decision.
- Inviting teammates isn't blocked for inactive workspaces (invitations aren't CRM records).
- Plan limits (e.g. seats for Starter vs Team) aren't implemented; the two plans differ only in price.
- In development the CSP allows `'unsafe-eval'` (React dev tooling) and inline styles. `upgrade-insecure-requests` is sent only when `APP_URL` is https.
- If a checkout completes but the webhook can't be delivered (e.g. local dev without `stripe listen`), the workspace stays inactive. The README explains how to forward webhooks locally.
